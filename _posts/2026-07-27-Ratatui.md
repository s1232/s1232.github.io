## Terminal user interfaces - the 2025 backdrop
It seems terminal user interfaces are back in popularity with the introduction of Claude and Cursor. Clutter-free and efficient user interfaces is the opposite of what many websites offer. An efficient terminal user interface is a beautiful piece of human - computer interaction. It is also a blast from the past. In the early 2000s I watched colleages using [AS/400 terminals](https://en.wikipedia.org/wiki/IBM_AS/400) and there is nothing that could beat the level of efficiency they had.

In addition, most terminal apps requires a very moderate amount of RAM and weighs nothing compared to the popular desktop apps like Slack, VS Code, browser tabs and Intellij. Laptops boasting 32 gigs of RAM are no longer special, but last year (2025) we saw RAM pricing raising 4x from the AI industry driving up consumption. So device makers have clear incentives to keep the RAM offerings from growing further.  

![RAM prices](/images/ram_pricing.png)

Terminal user intefaces can easily be used over a connection and is quite portable running equally fine on a Macbook, Android phone or a Raspberry PI. By versioning configuration files the user environment can be replicated across systems, something which is quite cumbersome for regular desktop apps. 

On a personal level, I use the terminal a lot. For the last two-three years I have been enjoying [Helix](https://helix-editor.com/), [Alacritty](https://alacritty.org/), [Zellij](https://zellij.dev/) and [Nushell](https://www.nushell.sh/), without being a power user in any of these.


So, the terminal offers:

- Low resource usage
- Efficient interaction
- Portability
- Remote friendliness


## Developing for the terminal
One thing is using and appreciating the terminal, but why develop for it? I am currently learning Rust and I need the capability to build some sort of user interface, beyond just command line interfaces. There are plenty of web Rust web frameworks like Actix and Axum and there are even those that offers front-end implementations in Rust, like Dioxus and Leptos. However, the learning curves seem just as steep as the one for building TUIs using Ratatui and deployment complexity is far greater.

So the current plan is to use Ratatui, but deliberately learn first principles as a valuable side effect:

- Immediate mode rendering
- The Elm Architecture (TEA)

These are general elements of building user interface, transferable to many other frameworks and stacks.

## The Elm architecture
Building user interfaces is not without complexity. We want to apply an application architecture, to avoid buildinga complete mess. The Ratatui website describes a few application patterns, the ELM architecture *(TEA)* being one of these. It has a *Model*, *Udate* and a *View*. 

- State is kept in the Model. The model is in principle immutable but it is kosher to mutate it when using Ratatui.
- Update. Decides how to mutate the model based on user inputs or events. Typically, `enum Message`, each variant representing an event type.
- Update. Function that mutates or create a new model based on the event. Match on the Message enum and process each variant. 

## Decision: With or without Tuirealm
The [tui-realm crate](https://crates.io/crates/tuirealm) offers state management, a component model, focus and subscription management and a set of widgets built on top of Ratatui. It is mentioned in the [introduction to the ELM architecture](https://ratatui.rs/concepts/application-patterns/the-elm-architecture/) of the Ratatui documentation. On the other hand, it is also a fairly small crate, maintained by a single individual.



## Mini-clossary##

### Immediate mode
Ratatui is using *immediate mode*, different from *retained mode*. When an event occurs it (immediately) draws the UI by diffing against the existing terminal buffer and renders a partial update. When first reading about immediate mode, I mistook it as a game rendering loop that execute every tick of the display refresh rate at for instance 120Hz. In immediate mode updates are triggered and not constantly looping.

In *retained mode* the application builds a persistent tree of UI elements, maintaining and redrawing these as needed.

### Raw mode
When building a TUI application - the terminal's raw mode typically used, which gives "full control" to the application. For instance, each key press is submitted directly rather than added to a line buffer and hitting ENTER no longer triggers a line feed.

### Alternate screen
Alternate screen. The application is not rendered into the existing terminal view, but to a separate full screen view. On exit, the terminal is restored to the state right before the application was launched.
